# 日次ポッドキャスト配信ランブック

毎日の学習系・ニュース系ポッドキャスト配信を、同じ型で実行するための手順書。
初版は 2026-11-14 の実走と、その後のユーザーFB修正で確定した内容に基づく。
自動化（my-life #90）の仕様が固まるまでの運用基準であり、実行のたびに気づきを追記する。

## 0. 参照先（固定）

| 対象 | 場所 |
|---|---|
| 学習教材 | my-docs `security-study/<シリーズ>/Day<N>_study.md` |
| ニュースレポート | my-docs `security-news/cybersecurity_news_YYYY-MM-DD.md` |
| 学習ノートブック | NotebookLM「30日間資格学習」 |
| ニュースノートブック | NotebookLM「サイバーセキュリティニュース」（収集用）。音声化は原則「レポートファイルをソースにした新規ノートブック」 |
| レポート形式 | ニュースノートブック内の `_Report_Template` |
| note アカウント | centervil（clever_chives813） |
| Spotify 番組 | 「30日間で学ぶ資格勉強」「AI CyberSecurity News Digest」 |

番組テンプレート（NotebookLM のフォーカス文に使う。**貼るのは1回だけ**。二重貼り付けが過去に常態化していた）:

- 学習系: 「以下のPodCastとして話して。番組名：「30日間で学ぶ資格勉強」番組内容：「本ポッドキャストは、自分用の資格勉強を目的として、AIが毎日自動生成する解説を配信しています。」」
- ニュース系: 「以下のPodCast番組として話して。番組名：「AI CyberSecurity News Digest」番組説明：「本ポッドキャストは、自分用のサイバーセキュリティ関連ニュースの情報収集を目的として、AIが毎日自動生成する解説を配信しています。世界中で起きたサイバー攻撃や脆弱性情報、セキュリティ動向をAIがまとめていますが、内容には事実と異なる部分や誤りが含まれる可能性があります。そのため、参考情報としてご利用ください。」」

## 1. 対象の確定（最初に必ずやる）

- [ ] 学習系の対象 Day = **Spotify の最新公開エピソードの Day + 1**。note の最新記事・NotebookLM の最新音源でも突き合わせる（3点が一致しない場合は最も遅れている工程に合わせる）
- [ ] ⚠️ **my-docs の `security-study/current_day.txt` を配信対象の根拠に使わない**。あれは教材生成側のカウンタで、教材追加のコミットで先行して増える（2026-11-14 実測: 値は 13、実際の配信対象は Day11）。シリーズ名は `security-study/current_theme.txt` で確認できる
- [ ] 対象 Day の教材ファイルが my-docs に存在することを確認する
- [ ] ニュースの対象日 = **前日**（JST）。`security-news/cybersecurity_news_<対象日>.md` が my-docs に既にあるか確認する（あればそれが正。作り直さない）
- [ ] 当日の準備フォルダ等の先行成果物がないか確認する（並行実行者がいる前提。2026-11-14 はレポートが実行中の 16:13 に別経路でコミットされていた）

判断ルール: 各工程の開始時に「成果物が既に存在しないか」を必ず確認し、存在すればそれを使う。

## 2. ニュースレポート（my-docs に無い場合のみ）

- [ ] 収集の定義: 実行時点から過去24時間（JST）、記事ページのみ（索引・トップページ不可）、出典必須、対象日は前日で日付づける
- [ ] `_Report_Template` の形式でレポート化し、`security-news/cybersecurity_news_<対象日>.md` として my-docs へ保存する
- [ ] 従来手段は NotebookLM Deep Research だが停滞実績がある（§7）。将来は agy 汎用 Skill（対象＋フォーマットを渡すと整形済み記事を返す）が本命

## 3. 音声化（NotebookLM、本番前提）

学習系:
- [ ] ノートブック「30日間資格学習」で、前日のソースと音源を削除し、対象 Day の教材を raw URL でソース追加する
  - `https://raw.githubusercontent.com/centervil/my-docs/refs/heads/main/security-study/<シリーズ>/Day<N>_study.md`
- [ ] 音声生成: 形式=詳細、言語=日本語、長さ=デフォルト
- [ ] フォーカス文 = 「<その日の教材テーマ>を初心者向けに解説して。」+ 学習系テンプレート（1回だけ）

ニュース系:
- [ ] レポートファイルを raw URL でソースにした新規ノートブックを作る（ノートブック名は「<対象日>のサイバーセキュリティニュースまとめ」形式）
- [ ] 音声生成: 形式=詳細、言語=日本語、長さ=短め
- [ ] フォーカス文 = 「<その日の主要トピックを要約した1文>」+ ニュース系テンプレート（1回だけ）

共通:
- [ ] 生成が終わったら M4A をダウンロードし、ファイル形式とサイズを検証する
- [ ] 生成前に前日の音源をダウンロードして退避しておくと安全（学習系はノートブック内が1世代しか残らない）

## 4. Spotify（下書きまで作り、公開はゲート）

メタデータ導出規則:

| 項目 | 学習系 | ニュース系 |
|---|---|---|
| タイトル | `<シリーズ名> Day<N>`（例: CRISC Day11） | `<対象日>サイバーセキュリティニュース`（例: 2026年11月13日サイバーセキュリティニュース） |
| 概要 | 音源タイトル（NotebookLM が付けたタイトル） | 同左 |
| シーズン | シリーズ通し番号（CRISC = 19） | 1（固定） |
| エピソード | Day N | 前回 + 1（通算） |
| アート | 番組のシリーズアート（デフォルト） | 同左 |

- [ ] エピソードを作成し、レビュー画面で全項目を確認して下書きとして残す
- [ ] 文字起こし/チャプターは自動生成がデフォルト（設定不要）
- [ ] コメントは番組単位設定。学習系番組は現在 Off で、切替が Spotify 側エラーになった実績がある → 公開ゲートで必ず提示する

## 5. note（下書きまで作り、公開はゲート）

記事の型（両系共通）: **定型文 → Spotify 埋め込み → 目次 → 本文**
- 定型文: 「この記事の内容はPodCastとしても配信しています。（最新記事以外は過去の配信回をご参照ください）」
- 埋め込み: 番組の Spotify リンク（学習系 show / ニュース系 show）。**貼っただけではテキストリンクのまま**なので、リンク末尾にカーソルを置いて Enter し、埋め込みプレイヤーに変換する
- 本文: **元ファイルの内容そのまま**を note 形式に変換する（書き直し・要約は禁止）
  - 学習系 = 教材ファイル全文。ニュース系 = レポート全文（まとめ＋詳報）
- 見出しレベル対応: 先頭の `## 📚 今日の学習テーマ` のみ小見出し（h3）、他の `##` は大見出し（h2）、`###` / `####` は小見出し（h3）。ニュース系はレポートの `#` 見出しが記事タイトルになるため本文には入れない

複製の落とし穴（毎回チェック）:
- [ ] ヘッダー画像は複製で引き継がれない → 前日記事と同じシリーズ画像をアップロードする。前日記事の画像 URL は note API（`https://note.com/api/v3/notes/<前日記事ID>` の `eyecatch`）から取得できる
- [ ] 目次ブロックが本文と一緒に消えていることがある → 埋め込みの直後にあるか確認し、無ければ挿入する
- [ ] 埋め込みがテキストリンクのままになっていないか確認する

公開設定（公開フロー内で設定）:
| 項目 | 学習系 | ニュース系 |
|---|---|---|
| タイトル | `<シリーズ名> 30日間学習Day<N>` | `<対象日> サイバーセキュリティニュースまとめ` |
| ハッシュタグ | #CRISC（シリーズのタグ） | #ニュース #セキュリティ |
| マガジン | `<シリーズ名> 30日間学習` | サイバーセキュリティーニュース（正式名は長音あり） |
| 価格 | 無料 | 無料 |

## 6. 公開ゲート（必須）

- [ ] 4点（Spotify ×2、note ×2）が下書きで揃ったら、タイトル・概要・対象日をまとめて報告し、ユーザーの承認を得る
- [ ] 承認後に公開する。埋め込みは番組リンクなので、note と Spotify の公開順は問わない
- [ ] 公開後に各 URL と公開時刻を報告する
- [ ] ログイン画面に当たったら「要操作：◯◯へのログイン」と報告して止まる（認証情報は扱わない）

## 7. 失敗時の代替手順

| 事象 | 対処 |
|---|---|
| NotebookLM の生成表示が固着 | 実体は完成していることが多い。ページをリロードして音源の有無を確認する（2026-11-14: 表示は約22分固着、実体は約8分で完成） |
| Deep Research が進まない | 30分進展がなければ停止する。代替収集（Web 検索）で候補を集め、レポートを my-docs へ保存してから音声化に進む |
| 保存先に既にファイルがある | 並行実行者の成果物の可能性。内容を確認し、問題なければそれを正として進める（上書きしない） |
| Spotify のコメント切替エラー | そのまま公開ゲートで提示し、ユーザーの判断を仰ぐ |
| note の貼り付けで見出しが化ける | 番号付き見出しが自動リスト化することがある。リスト書式を外してから見出し化し、番号は文字として入れる |

## 8. 実行チェックリスト（コピーして使う）

```
対象: 学習 Day__ / ニュース ____-__-__
[ ] 対象確定（Spotify最新+1、note・NotebookLMと突合、current_day.txt不使用）
[ ] 先行成果物の確認（my-docs のレポート有無、当日準備物）
[ ] 音声: 学習（ソース入替→生成→DL検証）/ ニュース（新規NB→生成→DL検証）
[ ] Spotify 下書き ×2（メタデータ規則どおり、レビュー確認）
[ ] note 下書き ×2（型・verbatim・画像・目次・埋め込み変換）
[ ] 公開ゲート報告 → 承認
[ ] 公開 ×4 → URL・時刻を報告
[ ] 気づきを GitHub に記録（このランブックの追記 / Issue / #90 コメント）
```

## 9. 気づき・自動化時の考慮点

- 状態（次の Day・対象日・工程ごとの進捗）は1ファイルのメタデータ SSOT に集約するのが本命（工程ごとに進みがズレるため、進捗は工程別に持つ）。各工程が自分の進捗を書き戻す方式で、ポーリングはしない
- シリーズ画像（ヘッダー・アート）はファイルとして SSOT 側に置く。note には過去画像のライブラリがない
- 番組テンプレートはクリップボードではなく SSOT に置く（二重貼り付け事故の根絶）
- セッション維持（NotebookLM / note / Spotify）が無人化の前提条件。特に Spotify はセッションが切れていた
- agy Skill は「ニュース専用」ではなく汎用（対象＋フォーマット → 整形済み記事）。OpenCode が Web 収集 MCP のように呼べる形も狙う。最終形は毎日自動実行 → my-docs へ Push
- 音声化は当面 NotebookLM が本番。Open Notebook は評価扱いで、判断条件は Podcast の聴き比べ
- note 記事生成は過去にスクリプト化で失敗した経緯があるため、安定するまでは Muse 支援で回しながら改善する
