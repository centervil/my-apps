## 設計詳細

### 1. 接続先アカウントの明示と本番保護（対策1）
- 環境変数 `NOTE_ACCOUNT_URLNAME` または `NOTE_TARGET_ACCOUNT` にて「想定する接続先アカウントの urlname」を指定する仕組みを導入する。
- 起動時に note API (`https://note.com/api/v1/users/me` または同等の認証ユーザ情報 API) から現在ログイン中のアカウントの urlname を取得し、環境変数指定値と厳密に照合する。不一致の場合は `AuthError` (`ACCOUNT_MISMATCH`) をスローし即座に終了する。
- テスト用操作（テスト記事の作成、テスト用削除）は、指定されたアカウントがテストアカウント（例: `urlname` が `centerviltest` 等、または設定されたテストモード環境変数）である場合にのみ許可し、本番アカウント (`centervil`) に対しては構造的に拒否・警告する。

### 2. 削除の許可リスト方式と行特定厳密化（対策2）
- 削除ロケータ (`NoteEditorPage.deleteNote`) において、引数で渡された `noteId` が、事前定義された許可リスト台帳ファイル (`credentials/note-deletion-whitelist.json` または環境変数・明示台帳) に記録された検証用キーと一致することを義務付ける。台帳にないキーの削除は例外をスローし拒否する。
- 削除対象行の特定を厳密化: ページ全体を対象にする `.first()` / `.last()` などの曖昧な指定を廃し、対象キーのアンカー (`a[href*="${noteId}"]`) を起点とした固有の祖先要素行内でのみメニューボタンおよび削除ボタンを特定する。行特定ができない場合は削除操作を実行しない。
- 削除前後で WebUI 上の目視確認（一覧から対象が消えていることの確認）を必須ステップとしてログに記録する。

### 3. 公開ゲートの厳密な品質測定と自動修復・ロールバック（対策3）
- 公開後に公開 API またはエディタ上で実施する品質チェックに、以下を追加・強化する:
  - 本文 verbatim チェック
  - 目次要素 (`.toc` または目次ブロック) の存在確認
  - Spotify 埋め込みプレイヤーの変換確認
  - ブロック順の妥当性確認
  - **空段落数** (`emptyParagraphCount <= 5`) の厳密なカウントと判定
- 1つでも fail の場合は「公開完了」とせず、終了コード 1 (`QUALITY_CHECK_FAILED` または `PUBLISH_SETTINGS_FAILED`) を返す。
- フェイル時は自動修復（再レンダリング/再適用）を1回行い、それでも駄目な場合は自動的に非公開に戻す (unpublish) かエスカレーションする構造を組み込む。

### 4. テスト作成の隔離と削除凍結（対策4）
- 検証フローは既定で下書きのみを作成。本番への公開を伴うテスト作成は、明示フラグ `--publish` かつ許可リストへの登録がある場合のみ許可。
- 許可リストが入るまで、本番アカウントへの削除操作は全面凍結とする。
