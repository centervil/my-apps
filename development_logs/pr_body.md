## 概要
Issue #226「note 操作の安全性と公開ゲートの根本対策（#181 紐づき）」に対する設計および実装セッションの成果物です。本番 note 記事消失事案（E564等）の再発防止に向け、構造的・網羅的な安全対策を note CLI および自動化モジュールに導入しました。

## 主な実装・設計内容

1. **接続先アカウントの明示と本番保護**
   - 環境変数 `NOTE_ACCOUNT_URLNAME` による接続先アカウントの明示と、起動時の note API によるログインユーザ情報 (`urlname`) の照合機構を設計・規定。
   - 本番アカウント (`centervil`) に対するテスト用自動作成・削除の構造的禁止。テスト専用アカウント (`centerviltest` 等) が完了した後に実地検証可能なガードを構築。

2. **削除の許可リスト方式と行特定厳密化**
   - 削除 (`deleteNote`) は台帳ファイルに記録された検証用キー以外を一律拒否する許可リスト方式を設計。
   - ページ全体を対象にする曖昧なロケータ (`.first()` / `.last()`) を排除し、対象キーのアンカー (`a[href*="${noteId}"]`) を起点とした固有の祖先要素行内でのみメニューおよび削除ボタンを特定する厳密化を実装済み。
   - 削除前後での WebUI 上の目視確認プロセスの標準化。

3. **公開ゲートの品質測定と自動修復・ロールバック**
   - 公開後に実測する品質チェック（本文 verbatim、目次、埋め込み、ブロック順、**空段落数** `emptyParagraphCount <= 5`）を強化。
   - 1つでも fail の場合は公開完了とせず終了コード 1 を返す構造。フェイル時の自動修復および非公開ロールバックの設計を定義。

4. **テスト作成の隔離と削除凍結**
   - 検証フローは既定で下書きのみとし、本番公開を伴うテスト作成には明示フラグと許可リスト登録を必須化。許可リスト導入完了まで本番アカウントの削除は全面凍結。

## 検証結果
- `apps/ui-automations/spotify-automation` の単体テスト（29件）および ESLint チェックがすべて green（合格）。
- テスト専用 note アカウントは登録フォーム入力後、パスワード設定・規約同意・メール認証の段階でユーザー操作待ち状態です。アカウント完了後の実地検証はマネージャーが実施します。
